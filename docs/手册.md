## 2. 功能详解

- **策略下发是本组件唯一真正对外的"判权限"相关能力**：`GET /authz/bundle` 现算现返（`roles`/`role_permissions` 永远热、几百行恒小，不需要缓存），`ETag` 是整份 JSON 的 SHA-256，`If-None-Match` 命中就返回 `304` 空 body。
- **stale_since 是两个来源的 UNION**（`bundle.go` 的 `loadStaleSinceInto`）：`role_changes` 表（管理员显式的 `granted`/`revoked`/`kicked` 三种动作）与 `user_roles.expires_at`（自然到期，不需要任何人在到期那一刻写一行——纯粹从落在窗口内、且已经过去的 `expires_at` 推导）。两者都按 `sub` 取窗口内更晚的时间戳。窗口大小固定为 `2 × accessTokenTtlSeconds`。
- **角色内容变更不触发 stale_since**：给一个角色勾/取消一个权限键，靠 bundle 的 `roles` 字段在下一次轮询（~15 秒）直接刷新——不需要让任何已签发的 token 失效，因为角色本身没变，变的只是它对应的权限集合。
- **专属角色 `u:<sub>` 必须出现在 bundle 的 `roles` 里**（`ComputeBundle`/`loadRolesInto` 不按 `is_system` 过滤）——这与"管理界面的角色列表不显示专属角色"（`ListRoles` 按 `is_system = false` 过滤）是两条独立的判据，管的是两件不同的事：前者关系到持有专属角色的用户会不会静默失权，后者只是 UI 展示。混淆两者是本组件测试覆盖优先级最高的一类错误（见 `repo_test.go` 的 `TestComputeBundle_专属角色也出现在roles里`）。
- **自举**：迁移种下 `authz_admin` 角色与 `infra.authz.admin` 权限键的静态部分，`Start()` 读 `bootstrapAdminSub` 把这个角色幂等地授给客户特定的 sub——解决"第一个管理员从哪来"的问题，不引入任何超级用户/后门判定分支。
- **后台循环**（`module.go` 的 `Start`，两个并发跑）：Outbox 推送（两条旁路审计事件）+ 分区维护（`event_outbox` 周分区、`role_changes` 月分区，同一个 `partition.Start` 函数里两套独立的窗口逻辑）。**没有事件消费循环**——阶段三唯一的弱依赖 `mdm/org` 要到阶段五才存在，YAGNI。

## 3. 完整契约清单

**gRPC `infra.authz.v1.AuthzService`**（3 个 rpc，见 `contracts/infra/authz/v1/authz.proto`）：

| rpc | 类型 | 说明 |
|---|---|---|
| `BatchGetRoles` | 读，§3.8 强制的 batchGet | 查不到的 code 直接在结果里省略，不报错 |
| `ResolveClaims` | 读 | 给 `infra-iam-casdoor`：`sub -> roles[]/dept_path/org_id`。登录与刷新时各调一次，绝不缓存 |
| `GetBundle` | 读 | gRPC 版的策略下发，内容与 REST 完全一致（同一个 `service.GetBundle`） |

**REST**（见 `contracts/authz.openapi.yaml`，路径**不走** `/{domain}/{name}/**` 前缀）：

| 路径 | 说明 |
|---|---|
| `GET /authz/bundle` | 策略下发，不进 `edge_routes`，不经网关 |
| `GET /api/me/permissions` | 拉本人权限键集合（当前用调试 header 取 sub，见 README「已知缺口」） |
| `GET/POST/DELETE /api/admin/roles[/{code}[/permissions[/{key}]]]` | 角色 CRUD + 权限键勾选 |
| `GET/POST/DELETE /api/admin/users/{sub}/roles[/{code}]` | 用户-角色分配 |
| `POST /api/admin/users/{sub}/permissions` | 给人单独加一个权限（走专属角色 `u:<sub>`） |
| `POST /api/admin/users/{sub}/revoke` | 踢人：撤销全部角色 |
| `GET/POST /api/admin/departments`、`POST /api/admin/users/{sub}/department` | 阶段三极简部门表 |

**发布事件：** `infra.authz.role.changed.v1`、`infra.authz.user_role.changed.v1`（均为旁路，仅供 `infra-audit`）。
**消费事件：** 无（阶段三）。`mdm.org.department.changed.v1` 是阶段五才会有的消费方。

详细字段与判据见设计计划 `docs/design/infra-authz.md`——那份是真相源，这里是速查表。

## 4. 数据模型

| 表 | 分区 | 唯一约束 / CHECK | 说明 |
|---|---|---|---|
| `permissions` | 不分区 | `key` 主键 | 权限键册镜像，`config.permissionCatalog` upsert 进来，只增不改（`deprecated` 列人工维护） |
| `roles` | 不分区 | `code` 主键 | 角色用字符串自然键，不是 bigserial——bundle 按这个代码组织，省一次 join |
| `role_permissions` | 不分区 | `(role_code, permission_key)` 主键，两个外键 | 角色 → 权限键 |
| `user_roles` | 不分区 | `(sub, role_code)` 主键 | `expires_at` 为 NULL = 永不过期；按 `expires_at` 建部分索引（`WHERE expires_at IS NOT NULL`），bundle 生成要扫窗口内到期的行 |
| `role_changes` | `changed_at` **月** 分区 | `CHECK change_type IN ('granted','revoked','kicked')` | stale_since 的来源，只记"人的角色变了"，不记角色内容变更、不记"expired"（到期直接从 `user_roles.expires_at` 推导，不需要写行） |
| `departments` | 不分区 | 无 | 阶段三临时表，`dept_path` 含自身的祖先链（如 `/1/12/`），插入时先拿到 identity 生成的 id 再回写路径 |
| `user_departments` | 不分区 | `sub` 主键 | sub → department，`ResolveClaims` 的 `dept_path` 来源 |

另有全组件通用的 `event_outbox`（周分区，只发不收——本组件没有 `event_inbox`）。

**实测验证**（真跑在 `infra_authz` schema，非 mock）：专属角色的权限键正确出现在 bundle 的 `roles` 里、`ListRoles` 正确排除专属角色、`stale_since` 分别从 `role_changes` 与 `user_roles.expires_at` 两个来源正确推导且窗口外的变更不出现、重复授予同一到期时间不重复记账而到期时间真的变化才算一次新变更、撤销不存在的分配是安全无操作、踢人只记一条 `role_changes`（不是每个角色一条）、`permissionCatalog` 同步只增不改绝不删除已发布的 key、`u:` 前缀创建角色被拒绝、部门树的 `dept_path` 前缀关系正确、up/down 迁移在空数据下可完整往返。

## 5. 开发

```bash
export TEST_PG_DSN="postgres://postgres:<密码>@localhost:5432/brickkit_db?sslmode=disable"
go test ./... -race -count=1
```

跑测试前必须先用真的迁移工具把 `infra_authz` schema 建出来（测试连的是真库，不是 mock）：

```bash
export DATABASE_USER=postgres DATABASE_PASSWORD=<密码> DATABASE_HOST=localhost DATABASE_PORT=5432 DATABASE_NAME=brickkit_db PG_SCHEMA=infra_authz
go run ./backend/cmd/migrate up
```

**核心测试**是 `backend/internal/repo/repo_test.go` 的 `TestComputeBundle_专属角色也出现在roles里`——去掉 `loadRolesInto` 里"不按 `is_system` 过滤"这条判据后手动验证过，这条测试会稳定报"专属角色应该出现在 bundle.Roles 里"失败。**改 bundle 计算逻辑后必须重跑这条测试。**

⚠️ 这个 schema 里有一条真实的种子数据（`authz_admin`/`infra.authz.admin`，来自 003 迁移）——测试用 `uniqueID` helper 给每次测试造独立前缀的 role code/权限键/sub，不会撞上种子数据，但**不要**假设 `permissions`/`roles` 表在测试开始时是空的。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| `ComputeBundle` 报 `sql: Scan error ... storing driver.Value type string into type *[]string` | pgx 的 `database/sql` 通用接口不会自动把 PostgreSQL `text[]` 解成 Go `[]string`（`array_agg` 的结果直接 `Scan` 进 `*[]string` 会报这个错，真机测试踩出来的，见 `bundle.go` 的 `loadRolesInto` 注释） | 不用 `array_agg`，改成逐行 `LEFT JOIN` 在 Go 里收集——`loadRolesInto` 现在就是这么写的，不要改回 `array_agg` |
| 持有专属角色 `u:<sub>` 的用户在业务组件里完全没有任何权限，且没有任何报错 | `ComputeBundle` 的 roles 查询被误加了 `WHERE r.is_system = false`（很容易联想成"专属角色是内部实现细节，bundle 里应该也隐藏"——这个联想是错的） | `ComputeBundle`/`loadRolesInto` 绝不能按 `is_system` 过滤；`is_system` 只用来控制 `ListRoles`（管理界面看不看得见）这一个判据 |
| 迁移报 `role_changes` 的 `role_code` 违反外键或 `change_type` 违反 CHECK | 试图记录一条 `change_type = 'expired'` 的行 | 不需要——到期不需要任何人写一行 `role_changes`，`loadStaleSinceInto` 直接从 `user_roles.expires_at` 落在窗口内的行推导 |
| `GrantUserRole`/`RevokeUserRole` 重复调用却仍然不断产生新的 `role_changes` 行 | 传入的 `expiresAt` 每次都用 `time.Now()` 现算，两次调用的值必然不同，触发 `WHERE user_roles.expires_at IS DISTINCT FROM EXCLUDED.expires_at` 判定为"变了" | 到期时间应该是业务上真正想要的绝对时间点（如"到 2026-12-31"），不要用相对时间现算；幂等判定依赖的是"两次传入的值是否字面相同" |
