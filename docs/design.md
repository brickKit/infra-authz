# infra/authz 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、命令、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试、设计取舍在 `AGENTS.md`；成员的义务在族契约 `contract-infra-authz` 的 README；规则全文在装配项目的安全 01–10（尤其 03 视图与核验、04 管理上限、07 包含证明、08 生效点与记录、09a 记录与错误、10 成员切换）与协议 03、15。

## 边界

授权族的默认成员：保存安全记录，只在生效点改变它们；接收各组件提交的资源定义；按已提交的记录给每个组件计算授权视图。所有部署都需要一个授权成员。

| 不在这里 | 归谁 |
| --- | --- |
| 账号、登录、令牌 | 身份成员（`infra/iam-*`） |
| 法人与部门（组织维度的来源） | `mdm/org`（经投影取得） |
| 员工与任职（任职关联授予的来源） | `mdm/employee` |
| 每个请求的判定 | 各组件的 SDK 用本组件下发的视图在本地判定（安全 03 的有界本地授权） |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 资源定义 | 组件启动时提交的资源类型、维度、字段与操作；只接受注册表登记的属主提交 | `be.security.resource_definition`、`DefinitionService.Submit` |
| 安全记录 | 授予、角色修订、管理职责单元与持有资格等；记录是权威，引擎只是索引 | `security_record` |
| 完整授予与段 | 一份授权：操作、范围（段，每个维度一个原子的“与”）、条件与字段 | `grant`、`segment` |
| 角色、任职关联授予、共享与委托 | 角色是权限的并集；任职关联授予随任职生效与结束（D30）；共享把资源给接收人，委托由受托人代办（安全 05，本版不做） | 安全 04、05 |
| 管理职责单元 | 机构的授权管理边界：所管范围、允许的管理动作、可授出的上限 | `management_unit` |
| 包含证明 | 授出的段必须在授出者的上限之内，逐维比较；生效点现场证明，不复用旧的见证 | 安全 07 |
| 生效点 | 改变安全记录的那个本地事务；放宽只在这里检查通过才生效 | `effectpoint.Effect`（`internal/effectpoint/change.go`） |
| 安全修订 | 每个生效的变更推进的序号；本版只有一个域 | `authz.security.deployment` |
| 自然人 | 关联到同一员工的全部有效账号算一个人：确认人的独立性、安全处置的账号集合按它判断（安全 02、08） | `employment.PersonOf`、`effectpoint.Independent` |
| 任职绑定 | 授予或管理持有带 `appointment`：任职在职、账号关联到它的员工时才算；任职结束或关联结束，视图立即不给、闭包记为 `source_ended`（安全 04、D30 的前一半） | `employment.Binding` |
| 视图 | 一个组件本地求值用的授权快照，带有效期与安全修订；每次核验在主库上重新计算 | `ViewService.Verify` |

## 拥有的数据

安全记录（授予、角色、管理职责单元与持有、以后的共享、委托、扮演会话）、资源定义与权限目录、视图所依据的修订、变更键与最终拒绝的绑定、本组件的实例身份（`AUTHZ_INSTANCE`）。表在 `authz/migrations/`。安全记录与审计记录同一事务写入。

## 规则

- 记录是权威，引擎只是索引（安全 10）。
- 授予不超出授出者的管理上限：生效点现场做包含证明；包含规则表里没有的原子组合答“无法证明”，不放宽。
- 普通变更不能移除最后一个可用的授权管理员；来源侧的离职与停用照常生效，没有可用管理员时进入待恢复（安全 08、D62）。
- 每个生效的变更推进安全修订号，与审计记录同一事务写入。
- 视图每次核验都按已提交的记录重新计算，不缓存（安全 03）。
- 生效点用一把全部署的锁，变更一个接一个；最终的拒绝绑定变更键（同键重试得到同一结果），冲突与定义未到（`DEFINITION_PENDING`：引用的资源类型在注册表里有属主、它的定义还在提交中，D77）不绑定；注册表里没有的资源类型（写错的名字、这个部署没有运行的组件）没有什么在路上，答 `REQUEST_INVALID` 并绑定。
- 资源定义只接受注册表（`AUTHZ_REGISTRY`）登记的属主；本组件自己的键也要在注册表里。
- 本组件的用户面也受授权保护，它向自己核验自己的视图。

**安全来源与恢复**（设计）：高可用部署中全部写入同步提交（D66）；收紧先在事务外写意图证据，提交后经发件表写结论（协议 15）；整套恢复时按原提交序号重放证据，重放全部结束后才判定可用管理员是否为零。

## 记录的状态迁移

安全记录的状态只经一处写入（`effectpoint.Transition`），它按下面这张表核对“从哪里到哪里”，表里没有的迁移是缺陷，直接报错、整个事务回滚。表照安全 08 的“状态迁移”与“结果对记录状态的作用”；代码里是同一张表（`internal/effectpoint/lifecycle.go` 的 `moves`），单元测试逐行比较这里与代码。暂停（`held`）带暂停原因、结束（`ended`）带结束原因，写成 `held/<原因>`、`ended/<原因>`；“（新记录）”是插入时的状态。收窄是新的内容修订，不是状态迁移，不在表里。

| 从 | 可以到 |
| --- | --- |
| （新记录） | `requested`、`awaiting_confirmation`、`scheduled`、`active`、`ended/rejected` |
| `requested` | `awaiting_confirmation`、`scheduled`、`active`、`ended/rejected`、`ended/withdrawn`、`ended/cancelled` |
| `awaiting_confirmation` | `awaiting_confirmation`、`scheduled`、`active`、`ended/rejected`、`ended/withdrawn`、`ended/cancelled` |
| `scheduled` | `awaiting_confirmation`、`active`、`ended/rejected`、`ended/withdrawn`、`ended/cancelled` |
| `active` | `held/security_hold`、`held/uncomputable`、`ended/revoked`、`ended/relinquished`、`ended/superseded`、`ended/source_ended`、`ended/source_narrowed`、`ended/expired` |
| `held/security_hold` | `active`、`held/security_hold`、`held/restore_pending`、`ended/revoked`、`ended/relinquished`、`ended/superseded`、`ended/source_ended`、`ended/source_narrowed`、`ended/expired` |
| `held/uncomputable` | `active`、`held/security_hold`、`ended/revoked`、`ended/relinquished`、`ended/superseded`、`ended/source_ended`、`ended/source_narrowed`、`ended/expired` |
| `held/restore_pending` | `active`、`held/security_hold`、`ended/revoked`、`ended/relinquished`、`ended/superseded`、`ended/source_ended`、`ended/source_narrowed`、`ended/expired` |
| `ended` | — |

说明：

- `awaiting_confirmation` 到它自己：已保存的放宽再进生效点时确认不成立，重新保存为待确认（推进状态修订）。`scheduled` 到 `awaiting_confirmation`：管理员恢复作废它所依赖的确认，或到点时确认不成立。
- `ended/rejected` 从已保存的记录来：作业触发的放宽（确认齐全、到点）被终局驳回，不论哪一行。
- `held/security_hold` 到它自己：已被处置暂停的记录又被另一条处置或管理员恢复的撤换暂停。`held/restore_pending` 只从 `security_hold` 来：解除处置时没剩下有效段或超出预算。
- `held` 的记录不经闭包作业转成 `uncomputable`：已暂停的仍算不出时保持原状。

## 事件

安全记录变更（设计：收紧先在事务外写意图证据，提交后经发件表写结论，协议 15）；本版只有审计记录与安全修订，没有发布事件。

## 依赖

- 身份（必需）：令牌的公钥；账号状态，内部来源（水位来源，安全 03、D64）：本组件以带水位的投影 `accounts` 保存它（SDK 的 `projection.Watermarked`，补取与批量读取、快照是身份成员系统面上的标准方法 A115、A121），视图的主体条目带 `accounts_disabled` 与 `security_version`。数据库、消息系统（必需）。
- `mdm/org`（可选）：法人与部门维度，缺时这两个维度不可用；`mdm/employee`（可选，3.0.46 起）：第二个内部来源（水位流 `mdm.employee`，投影 `employees`，配置 `EMPLOYEE_COMPONENT`、`EMPLOYEE_GRPC_URL`），给出账号与员工的关联与任职；缺时每个账号自成一人、没有记录能绑定任职，`CheckLinkChange` 与 `Administrators` 不答任何调用方；`infra/audit`（可选，兼任证据存储）：收紧的意图在本地事务之外写入，缺或不可达时收紧照样生效，完整记录进入外部告警（协议 15）。内部来源按水位探测取得新鲜度（安全 03）。

- **自然人**：确认人不能与申请人、对象是同一个人（关联到同一员工的账号算一个人）——记录、处置的解除、计划、账号状态、账号关联的确认都按它判断，也不能确认本人员工的关联；员工来源此刻证明不了时答无法证明（按最后已应用的事实的收紧除外）。安全处置记下发起时这个人的全部账号，求值时再并上此后关联到同一员工的账号，新关联进来的账号逃不掉。
- **任职绑定**（安全 04、D30 的前一半，迁移 0019）：授予与管理持有可以带 `appointment`；授出时任职计划中或在职、受授账号关联到它的员工（`D_src_high`，证明不了可重试）；视图只在来源证明任职在职、关联有效时给（`D_src_read`），任职计划中、结束、证明不了都不给；任职是闭包的来源种类：任职状态变了、关联结束都登记闭包，记为 `source_ended`；整套恢复的 6.5 也按它记账。管理持有在任职结束与闭包之间按最后应用的事实判断可用（`HoldingsOf`），直接查表的地方（`OthersAvailable`）要等闭包，相差作业的延迟。

3.0.26（底层先行第 3 项 T4–T9；T4 随 3.0.17、T5 随 3.0.18–3.0.19、T6 随 3.0.20、T7 随 3.0.21–3.0.22、T8 随 3.0.23–3.0.24、T9 随 3.0.25–3.0.26 发布）：

- **生效点与记录**：按安全 08 的决策表（30 行，纯函数 `decide`）；变更请求与结果是 09a 的 `be.security.change_request`、`change_result`，按变更键查询。记录有六个状态、暂停与结束原因、状态修订与内容修订、前身与有效期。收窄是同一记录的新内容修订；续期与扩大建新记录，生效时以 `superseded` 结束旧记录；尚未生效的记录可以终止（收回、取消）。
- **待生效**：未来生效的放宽保存为 `scheduled`，在同一事务里登记到点的工作项（P7.24）；到点以派生键 `<记录>:<状态修订>:scheduled` 进生效点，重查请求者的资格与包含证明。状态或状态修订变了的作废（第 3 行）；处理中按业务等待放回、不计尝试（最多等 24 小时）；终局驳回把记录结束为 `rejected`；到点时前身已不再生效的续期终局驳回（A122）。
- **中性变更**（`direction: neutral`）：只改管理单元或角色修订的名称，新的内容修订与审计，状态修订与安全修订不动；候选里除名称外有别的不同，答“拆成收紧或放宽”；谁能改与收紧相同（根单元与角色修订由授权管理员）。
- **有效段**（安全 08）：视图给授予的段 ∩ 治理单元当前的上限，单元的上限是它的范围 ∩ 父单元的上限、逐级到根（`effective.go`，求交按安全 07 的原子表，表外的组合为空）；只有注册了、没有退役、属主仍定义着的权限键参与。上级单元收窄后，下级的授予在下一次核验里立即缩小，记录本身不动、仍然生效；生效点的包含证明也按这条链的上限。单元续期或扩大（新记录取代旧记录）后，指向旧单元的下级、持有资格与授予都归到新单元：上限、管理资格与闭包都按它。
- **闭包作业**（`closure.go`）：只记账，访问早在视图里缩小了。按依赖索引（记录的来源随记录同一事务写入）找出受影响的记录：单元或角色修订结束的 `source_ended`，有效段为空的 `source_narrowed`，求交算不出的 `held`（`uncomputable`），部分越界的标记待复核；推进状态修订、写审计，不推进安全修订。触发：单元或角色修订在生效点收紧；账号状态变化（事件、补取、对齐的快照与读回，SDK 的 `Projection.Changed`）。下级单元的闭包接着处理它自己的依赖。某种来源的索引不完整时不当作“无人受影响”：扫描这类来源可能影响的全部记录，把来源域记为待复核，扫描不再逐个单元连锁。
  - 账号：来源证明停用且没有安全标记、或账号已不存在，以它为来源的授予与持有资格结束为 `source_ended`；冻结、带被盗或可疑标记的停用是身份侧处置（T6），不结束任何记录；来源此刻证明不了时作业等待。
  - 有效期的终点：记录建立时登记一项到点的工作项，到点结束为 `expired`（求值时早已不给访问）。
  - `held`（`uncomputable`）的记录在来源重新可计算后（它的单元的闭包发现），以派生键 `<记录>:<状态修订>:restore` 进生效点（`restore_uncomputable`）：不重查原请求者（D36）；有效段为空的保持暂停（第 25 行），部分越界的生效并标记待复核（第 30 行）。暂停期间被收窄的记录推进状态修订，旧的恢复作废，它的单元的闭包按新内容重新登记（CP103、CP115）。
- **放弃本人的记录**（D82）：本组件自己的资源 `infra.authz.security_record` 有一个主体维度 `holder`（授予的受授人、持有资格的持有者），管理者的段对它取全部；本组件在自己的视图里给每个持有生效记录的主体一段“读取与放弃本人的记录”（`holder = self`），谁也不用授予，所以持有者看得到、放得掉自己的记录，别人的答“找不到”。
- **确认与受保护操作**（3.0.18，T5）：新建或扩大管理单元、授出管理持有资格（含系统角色）保存为待确认，确认齐全后由工作项以派生键进生效点（未来生效的转为待生效）；撤销或收窄别人的授权管理员持有资格要先附确认。确认人缺省是其他可用的授权管理员（A123）；部署所有者以离线密钥签名的确认（A124，`AUTHZ_OWNER_KEY`，工具 `cmd/owner-sign`）在收紧时随时可以代替，在放宽时只在没有别的可用管理员时可以。确认人可以拒绝待确认的记录。
- **冷静期**（3.0.19，A127，`cooling.go`）：所有者确认的放宽，在除申请人与对象之外有授权管理员于 24 小时内变得不可用时（最后一条持有资格结束或暂停于其间，或有生效持有资格而账号此刻证明不了），保存为待生效、冷静期满生效（`cooling_off_until`，期满不再重判）；期间任何可用的授权管理员（申请人除外）可以取消（否决，第 7 行）。申请人自己的变更在冷静期内结束或暂停的管理员仍算可用，所有者确认因此不能代替独立确认人（CP108）；生效而待补确认的持有资格是账号状态弄得不可用的，即使申请人的变更（例如解除处置）最后碰过它，也不算申请人弄的（3.0.25）。所有者确认的每次使用、每次进入冷静期都写审计与错误级日志（没有通知通道）。
- **安全处置的发起**（3.0.20，T6a，A128，`disposition.go`）：表 `authz_disposition`（09a 的 `be.security.security_disposition`）；处置权限是本组件的操作 `infra.authz.security_disposition.dispose`（只减少访问），处置上限就是管理上限：治理域是发起者管理的单元，暂停的范围要包含于它的有效上限，“全部段”只在根。处置时这个主体在该单元及以下治理的、与范围相交的授予，以及他在那里的管理持有资格转 `held`（`security_hold`，记下处置身份）；处置生效期间，视图里他的段（含查看与放弃本人记录的固定段）只要与范围相交就整段不给，“相交”保守：只有按安全 07 的表可证明不相交才放过。处置其他授权管理员是受保护的收紧（确认绑定他的管理员持有资格），不受最后管理员不变量约束。被处置暂停的授予可以续期（新记录生效但同样被挡，旧记录等解除时以 `superseded` 结束）；被处置的人不能放弃被暂停的记录（第 8 行）。
- **安全处置的解除**（3.0.20，T6b，`release.go`）：一个生效点事务：处置仍暂停（`security_hold`）的记录逐条恢复——之后被续期包含的以 `superseded` 结束（CP31），没剩下有效段的转 `held`（`restore_pending`）由闭包作业照 `restore_uncomputable` 重试——处置转已解除；整个解除的决定（请求者资格、确认、恢复中的管理结构放宽）只有一份，处理中、待确认、驳回时什么都不变。谁能解除：能在处置的治理域处置的人（身份侧与管理员恢复建立的只在根），不是被处置的人。解除授权管理员的处置是受保护的放宽：确认绑定处置身份与处置修订（迁移 0008，确认可以不绑定记录而绑定处置），所有者确认只在没有别的可用管理员时算。
- **身份侧处置的派生**（3.0.20，T6c，`signal.go`）：应用账号状态时（`Projection.Changed`，事件、补取、对齐的快照都经它），按本组件上次从这个账号得出的状态（表 `authz_account_signal`）判断转变：变为冻结、或带被盗或可疑标记的停用，就在生效点的守卫下建立来源为 `identity_side` 的处置（根、全部段，他的生效记录转暂停），证据记录身份为 `<账号>@<状态修订>`；已有生效中的身份侧处置时并入它的 `signal_ref` 集合并推进处置修订；第一次见到的账号、同一状态再应用一次、解除之后账号仍冻结时又加标记，都不算转变；身份侧解冻不解除。解除身份侧处置要列出要移除的证据，集合不空时处置保持生效、记录不动（确认照样用掉）。与整套恢复的重放、成员切换的导出导入随第 4 项与成员切换。

- **再下放与管理动作**（3.0.21，T7b，A131，`delegate.go`，迁移 0013）：管理单元带 09a 的 `management_actions` 与 `max_subdelegation_depth`（必填）。持有一个单元的人，在它及以下只能做它的有效动作——它自己的与它以上每个单元的交集：直接授出要 `grant`，按角色修订授出要 `bind_role`，收紧、取消授予要 `revoke`，建子单元、授出管理持有资格、收紧单元或持有资格要 `delegate_management`；`edit_role` 仍只给授权管理员，`share_governance` 这一版没有对应的操作。子单元的动作是父单元有效动作的子集，层数小于父单元的有效层数（自己的与父单元减一取小），在根下的层数不超过 `AUTHZ_MAX_UNIT_DEPTH`（起始 6，也是安装认领时根单元的层数），否则不包含（第 18 行）。收窄单元可以去掉动作、减小层数，不能加。单元续期时新的父链不能经过前身（`REQUEST_INVALID`）。迁移给已有的单元补上全部动作，层数为 6 减去它在根下的层数。
